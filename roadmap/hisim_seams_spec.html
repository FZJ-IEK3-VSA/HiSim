Spec: HiSim gets a layer map shaped as a diamond, enforced by one test; post-processing and economics read one frozen run record; every multi-module component lives in a folder; the tests tree mirrors the packages

Status: draft, revised on 2026-11-09 after the owner's review of the first draft (#1260): the stack became a diamond, the post-processing DTO is restored as the only input of post-processing, and the legacy cost path is deleted rather than refactored (bead hisim-legacy-cost-cutover-7300, P1). Nothing merged. Owner: Noah Pflugradt. Epic: hisim-ylxf (P1). Builds on: the four import lints (tests/test_renovisor_import_lint.py, tests/test_economics_import_lint.py, tests/test_energy_system_layering.py, tests/test_subcomponent_import_lint.py), the config layer rule (hisim/config/__init__.py), the heat-pump package #1241, roadmap/cost_spec.md §10 (the cutover), and beads hisim-repo-cleanup-o6a.15, o6a.4, o6a.29, o6a.31 and hisim-rust-ideas-9ks.2. All numbers were measured on origin/main at 911498220 (2026-11-09) by the scripts in agent-tmp/seams/ (not in the repository; the appendix lists their tables). The owner's goal, in his words: "start working on the seams for hisim to limit the blast radius of changes as much as possible."

1. Problem

HiSim has 356 Python modules under hisim/ (the inputs data tree excluded): 33 modules directly at the top level and 10 code packages. Four import rules are enforced today, each by its own test; everything else may import anything. Measured on main:

  • The eight code packages form one strongly connected component. Counting static imports only, config, the top-level modules, caching, components, postprocessing, setup_rules, energy_system and economics all reach each other. There is no package below which a change is safe.
  • Components, post-processing and economics import each other in every direction. 49 component modules import economics.facts, 31 import postprocessing.kpi_structure, 21 import postprocessing.capex_computation; the post-processing imports 9 component classes and 9 modules of the component model; economics imports 9 post-processing modules. The root is hisim/component.py, which imports both economics.facts and kpi_structure: every component depends on the cost engine and the post-processing through its base class.
  • The post-processing DTO eroded into a bag of live objects. PostProcessingDataTransfer once carried everything post-processing needed; today it holds wrapped_components (live component instances) and all_outputs, and post-processing calls methods on them: component_kpi_entries, get_cost_opex, capital_cost_data, write_to_report, weather_config, isinstance(component, Weather), ElectricityMeter.get_classname() in kpi_entry["description"]. 298 access sites in 9 files read through the DTO, 95 of them on live objects (§4.9). That is a duck-typed dependency no import lint sees, and it is why post-processing cannot run from a result directory or be tested without a simulation.
  • Cycles are hidden, not absent. No module-level cycle exists among top-of-file imports, because the cycles were broken by hand: 86 function-local imports of HiSim modules, 36 importlib.import_module calls (24 in components, "to avoid circular-import errors"), and a string import of hisim.economics inside postprocessing_main. With those counted, three module cycles reappear (8, 6 and 5 modules, §4.2).
  • Components import each other. 76 static and 14 lazy imports run between modules of hisim/components, against the black-box principle of system_docs/component_design_principles.md B.1: default connections naming another class, and shared helpers filed under components.
  • A change to one component touches the whole repository. #1247 (PV publishes its DC power) changed 3 component modules and 86 other files; #1241 (heat pump into a package) moved 5 modules and changed 62 other files. The twins, the goldens and the tests cannot say which of them a change affects.
  • The tests tree does not mirror the packages. 310 test files sit flat in tests/ beside 16 helper modules; 9 subdirectories hold 78 more.

2. Decisions

The owner's review of the first draft (2026-11-09, #1260) settled the shape; the rest is open (§12).

D1 — The map is a diamond, not a stack (owner, 2026-11-09). "I don't think a linear layer approach as drawn is useful. Postprocessing should be parallel, not on top of components." Consequence: one contracts layer at the bottom; components, post-processing and economics side by side above it as siblings that never import each other; an orchestration layer that owns the sequence; RenoVisor on top (§6).
D2 — The post-processing DTO is restored as the only input of post-processing (owner, 2026-11-09). "A long time ago it used to be that postprocessing got everything it needed in the postprocessing DTO object and didn't need any imports, but that eroded over time. I think restoring that makes sense." Sharpened in the review: the DTO is plain data and serializable; at the end of the run the orchestrator asks each component once, through the component interface, and freezes the answers. Consequence: §8; post-processing runs from a result directory alone and is tested with synthetic records.
D3 — The legacy opex and capex calculation is deleted, not refactored (owner, 2026-11-09). "The opex and capex calculations are to be fully replaced by hisim.economics." That is Phase 7 of roadmap/cost_spec.md §10, bead hisim-legacy-cost-cutover-7300 (P1). Consequence: this spec moves nothing of the legacy path into a contracts package; its violations go on the allow-list under that bead (§7.2).

3. Terms

  • Layer: a named set of packages and modules. A module imports only layers below its own, never a layer above.
  • Siblings: packages in one layer that never import each other. They meet only through the layer below them.
  • Contracts: the bottom layer. Plain values and typed records every other layer may import: configuration base, load types, units, logging, the run parameters, the KPI types, the cost-fact types of the new engine, the energy-port vocabulary, and the run record.
  • Run record (the DTO): the frozen, plain, serializable record of one finished run that the orchestrator builds and hands to post-processing and economics. Today's PostProcessingDataTransfer, minus every live object.
  • Orchestration: the layer that owns the sequence: build and wire, run the components, freeze the run record, start the AFTER_RUN rules, hand the record to post-processing and economics, write the results.
  • Package: a directory under hisim/ with an __init__.py. A component folder is a package under hisim/components/.
  • Public API of a package: the names its __init__.py exports (__all__). Everything else in it is internal.
  • Static import: at module level. Lazy import: inside a function. Hidden import: by importlib.import_module or __import__ with a string.
  • Class path: the dotted module path plus class name an energy-system file writes under class:.
  • Allow-list: the committed list of today's violations the lint tolerates, each with the bead that removes it. A ratchet is an allow-list that may only shrink.
  • Blast radius of a change: the tests, goldens and recorded files that can be affected by it.

5.1 How "affected tests and goldens" becomes computable

  1. Changed units. Map every changed file to its package or component folder through the layer map; a changed test to itself; a changed energy_systems/*.yaml to that twin.
  2. Dependents. Close the set upward over the measured import graph at package granularity (the lint computes it). Under the diamond a change in hisim.components.generic_pv_system affects the orchestration and RenoVisor, never post-processing or economics; a change in post-processing affects nothing below it and no golden KPI value (only the files it writes); a change in the contracts affects everything.
  3. Tests. The tests of every affected package are the directory that mirrors it (§10) plus the system tests whose twins contain an affected component (step 4). A test outside those directories is unaffected unless it imports an affected module.
  4. Twins and goldens. A twin is affected when an entry's class: lies in an affected package. The golden pairs are those twins' golden_references/<setup>__<params>.json. For #1247 that is 29 twins; for a change inside the district-heating component it would be the 4 twins that contain one, for the car the 2.
  5. Output. The pytest paths, the golden pairs and the twins to re-record, as input of golden-check.yml's --pairs and of a path-selected pytest run (scripts/affected_tests.py, a child bead). Marker-only selection stays for main; selective runs are for pull requests. Owner memory defers Pants, doc-only skips and affected goldens until this epic lands; steps 1–4 are what those need.

The rules, as the lint checks them (§7):

  1. Down only. A module imports layers below its own, never above. The contracts import nothing but the contracts.
  2. Siblings never import each other. Components, post-processing and economics meet only through the contracts. Inside the components column the order is subcomponents and the component model below the component folders.
  3. The orchestration imports every sibling and sequences them. Nothing else does: no sibling calls another, no sibling starts the rules.
  4. No sibling and no contract knows a component class. Post-processing and economics read the frozen run record only (§8); the record carries the component's class name as a string for display and never the class.
  5. Across a package boundary only the public API is imported: the package itself or a name in its __all__.
  6. A hidden import of a HiSim module counts as an import. importlib.import_module("hisim…"), __import__ and the module_name = "hisim…" string pattern are checked like statements; the registries that need them (the class loader, the rules registry, the CLI, the weather facade) are listed in the map.

8.2 How the record is built

  1. The run ends. The orchestrator (the simulator, for both modes) asks each component once through one method of the component interface, say Component.run_record(all_outputs, results) -> ComponentRunRecord, implemented in the base class from what every component already carries (component_name, component_id, config, display_config, cost_relevance, the declared ports) plus the two hooks a component may override today (get_component_kpi_entries, get_cost_facts). A component never sees the record of another.
  2. The orchestrator freezes the answers with the output metadata, the wiring, the parameters and the result frames into one RunRecord (hisim.contracts), a frozen dataclass of plain values and frames, serializable to the result directory (run_record.json beside the CSVs; the frames stay in their files).
  3. The orchestrator starts the AFTER_RUN setup rules on the record (RunResults today takes live components; it takes the record), then calls PostProcessor.run(record), then economics on the same record (Q13), then writes.
  4. hisim postprocess <result directory> rebuilds the record from the directory and runs post-processing again, as the Sankey CLI already does for its three JSON inputs (energy_balance/figure/inputs.py).

Payoffs. Post-processing imports nothing of the component model or the components, so the import lint and the fresh-interpreter check prove rule 4 (today 9 + 9 + 3 imports and 95 duck-typed reads); it runs from a result directory alone, so a chart or a KPI change needs no simulation to try out; it is tested with synthetic records, so tests/postprocessing/ becomes base and loses its component imports; a component's KPI and cost declarations become visible data in the result directory; and the record is the one place the cost engine and the post-processing agree on.

8.3 Migration order, relative to the cutover

  1. Record beside the live objects. The simulator builds the RunRecord and still passes the live lists; post-processing switches reader by reader (outputs, wiring, components, KPI entries) to the record. No result changes; the goldens prove it. Independent of the cutover.
  2. The cutover (hisim-legacy-cost-cutover-7300, its exit criteria in cost_spec.md §10.0) deletes the legacy cost path and with it the last method calls on live components.
  3. The live lists go. wrapped_components and all_outputs leave the DTO; the orchestrator starts the rules and economics; the fresh-interpreter check turns on. Only now does rule 4 hold.

Step 1 can start at once and does not wait for the cutover; step 3 needs it (Q14).

The 49 + 1 imports of economics.facts (CostRelevance on every component, ComponentCostFacts on the adopters of get_cost_facts) and the 31 + 1 imports of kpi_structure are the new engine's and the KPI declarations: 82 statements that still need the contracts layer. 12. Open questions for the owner

Each question gives the context, the options with their consequences, and a recommendation marked as such. D1–D3 are decided; nothing below is.

Q1. May components import each other at all? Today 76 static, 14 lazy and 24 hidden imports exist, in three groups: (i) shared helpers misfiled under components (configuration, dual_circuit_system, heating_curve's EmitterDesign): they move regardless; (ii) the modules of one component spread over several files (car, LPG, electrolyzer, fuel cell): one folder makes the import internal; (iii) default connections naming another class and its outputs, in both directions (building ↔ heat distribution, storage ↔ heat pump, EMS → nine components). Options for (iii): (a) allow a component folder to import another's public API for its default connections only, acyclically: impossible as long as both sides declare the connection, so the importlib dodges stay; (b) allow it cyclically through lazy imports inside get_default_connections_*, on a permanent allow-list: the lint then lies about the components; (c) forbid every import between component folders and move the default connections out of the components into data the wiring layer reads (the assemblies already express the same connections declaratively; config.channels already matches ports by tag): the imperative setups get their defaults from the same table through the simulator's connect_automatically. Recommendation: (c) as the rule, with (b) as the interim allow-list under one bead, so the folder PRs do not wait for it.
Q2. The class-path convention. A packaged component is spelled three ways today (§4.7). (a) The defining module (…more_advanced_heat_pump.heat_pump.MoreAdvancedHeatPumpHPLib, as #1241 chose): the path names the file to open, but every later reshuffle inside the folder changes recorded files, which is the churn this epic exists to remove. (b) The package (…weather.Weather): a folder can be reorganised without touching a twin, the public API and the recorded name coincide; #1241's three paths and 40 building files are rewritten once. Recommendation: (b), with the recorder deriving the path from the nearest package whose __all__ exports the class, so no __module__ pin is needed.
Q3. Alias period or clean break for moved paths. #1241 broke cleanly: an old path is refused with EF-10 and no hint. (a) Clean break plus the recorded mapping, so the refusal names the new path and the PR (the bead's "fail loudly, except where written down" read as: the entries make the message, not an alias). (b) An alias period in which entries younger than N releases resolve with a warning: convenient for external users with old files, but HiSim has no external declarative users today and an alias delays the rewrite of every twin. Recommendation: (a); the mapping file exists either way, so (b) can be switched on if an external user appears.
Q4. import-linter or HiSim's own test. §7.1. Recommendation: the own test: it sees the hidden imports, keeps the map and the allow-list in one document, folds the four lints into one, runs in pytest -m base and adds no dependency. import-linter stays the fallback.
Q5. The allow-list policy. §7.2: fix first, package-level entries, or a module-level ratchet with bead ids and stale-entry failure. Recommendation: the ratchet. Inside it: may a PR add an entry? Proposed: only with a bead id and the owner's approval; the test's failure message says so.
Q6. Where the CLI lives. Eight entry-point modules sit at the top level. (a) A package hisim/cli/ with hisim_main.py kept at the top as the documented script path (README, CLAUDE.md, AGENTS.md and the quality workflow run python hisim/hisim_main.py); (b) everything into hisim/cli/ and a two-line hisim/hisim_main.py that calls it; (c) leave them flat and list them in the orchestration layer. Recommendation: (b); the console script hisim=hisim.cli:main becomes hisim.cli.main:main.
Q7. Folder policy. The bead says "every component that spans more than one module". (a) Only those (seven folders, §9.1): least churn, two shapes coexist. (b) Every component in a folder, also the ~40 single-module ones: one shape, one test directory per component, at the cost of 40 trivial moves (no recorded-path churn if Q2 picks the package path and the folder is named after the module). Recommendation: (a) now, (b) folder by folder when a component is next touched, never as one sweep.
Q8. The tests layout. (a) Mirror the diamond (tests/components/car/, tests/energy_system/, …) with systems/ for tests that build several components and tooling/ for tests of scripts and CI: the path says what a test exercises, which §5.1 needs. (b) Group by topic (hydronics, DHW, electricity, costs): reads well, but a topic spans packages and the path says nothing a tool can use. Recommendation: (a) with systems/, tooling/ and _support/.

A package makes the column visible in the tree, at the price of rewriting 106 import sites of hisim.component in every open PR's path. Recommendation: not now; decide again when the stack of open PRs is short.
Q10. The record's scope. (a) Everything post-processing needs is in the record, and post-processing never opens a file of the result directory except to write: one input, one test fixture, rule 4 provable by import. (b) The record holds metadata and the frames' locations, and post-processing may also read the result directory's files (all_kpis.json, balance_report.json, the CSVs), as the Sankey CLI does today: smaller record, but two inputs, and a test needs a directory. Recommendation: (a), with the frames referenced by file when the record is serialized and attached when it is in memory; the Sankey CLI then rebuilds the record from the directory and uses the same path as a run.
Q11. Who computes a component's KPIs. Today 31 components implement get_component_kpi_entries(all_outputs, results) and post-processing calls it. (a) The component computes its KPI entries, the orchestrator calls it at the freeze and the record carries the entries: the knowledge stays with the device (a heat pump knows what its SCOP is), post-processing only aggregates; the component model keeps a dependency on the result frame type. (b) Post-processing computes every KPI from the results and the output metadata (tags, port roles): the component declares, never computes after the run; every KPI formula lives in one place and runs from a result directory; but 31 components' KPI code moves into post-processing, keyed by tag, and a device-specific KPI (a battery's cycles, a collector's efficiency) needs a tag per device. Recommendation: (a) for now, through the one interface of §8.2, so the record holds the entries as data; (b) KPI by KPI where a formula is the same for every device of a kind (energy sums, peaks, run hours), under the existing KPI address scheme.

(b) Inside hisim/config/: already the bottom, but config is about configuring. (c) Flat leaf modules at the top level: no new package, but the top level grows again. (d) The record stays in hisim/postprocessing/ where the DTO is today: then economics imports post-processing for it, against rule 2. Recommendation: (a).

(a) Yes: the record carries each component's cost facts, energy-flow facts and KPI source; build_evaluation_inputs(record); one freeze serves both consumers and the cost engine runs from a result directory too. (b) Economics keeps its own collection pass over the live components through the orchestrator: a second interface, and rule 4 needs a second proof. Recommendation: (a).
Q14. Migration order of the record relative to the cutover. (a) Record first (§8.3 steps 1 and 2 in either order, step 3 after the cutover): the readers switch one by one while the legacy path still runs on live objects; the cutover then deletes the last live calls. (b) Cutover first, then the record: a smaller record from the start, but every record step waits on the cutover's exit criteria (cost_spec.md §10.0), which include the parity report and RenoVisor runs.
