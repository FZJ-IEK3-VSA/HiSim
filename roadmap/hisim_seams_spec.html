1. Purpose

A change to one part of HiSim should touch only that part and the parts that use it. Today it does not: #1247 (the PV publishes its DC power) changed 3 component modules and 86 other files, and every component depends on the cost engine and on the post-processing through its base class. This spec names the modules, says for each which modules it needs and which need it, names the records that cross the seams between them, and describes the test that keeps new imports inside the graph while the old ones are removed bead by bead. The owner's goal, in his words (2026-10-19): "limit the blast radius of changes as much as possible."

2. Terms

  • Module: a Python file or package under hisim/. Module group (short: group): a named set of modules in system_docs/module_graph.yaml; a module belongs to the group of the longest prefix that is the module itself or a package above it. The names in this spec are the yaml's group names.
  • Needs / needed by: group A needs group B when A's may_import lists B; B is then needed by A. The graph is the set of these edges; it is acyclic.
  • Seam: an edge across which one well-defined thing passes, named on the edge in the drawing. DTO (data transfer object): a frozen record of plain values, frames and strings, with no method that computes anything and no reference to a live component, wrapper or output. Serializable, so it can be written beside the results and read back.
  • Live object: an instance with behaviour and state that the simulator uses while it runs: a Component, a ComponentWrapper, a ComponentOutput.
  • Violation: an import the graph forbids. Baseline: the committed list of today's violations, each with its bead. Ratchet: a baseline that may only shrink.
  • Registry: a module that loads another by a name known only at run time (the class loader of energy-system files, MAIN_CLASS); its imports by string are allowed for the groups the yaml names.
  • Driver: the code that runs one calculation from start to end: the energy_system executor for a YAML file, hisim_main for a Python setup, RenoVisor's run through the energy_system API.
  • Component folder: a package under hisim/components/ holding one component and its parts. Subcomponent: a device part with behaviour that several components embed. Shared code: a type, enum or pure helper two or more components use.

3. The two drawings

Both drawings use the same boxes in the same places. Proposed: the allowed graph of the yaml. A blue arrow is a seam, labelled with the record or interface that crosses it; a grey arrow is an allowed import with nothing special on it; a green dashed arrow is data or a call, not an import; an orange dashed arrow is a design choice the owner has not confirmed (§10). Arrows into the foundation (leaves, physics_constants, config, parameters, infrastructure, contracts) are not drawn, except the two faces of config; each box's footer lists them. Current: today's imports in the same positions, measured on 2026-11-09. Grey: an import the proposed graph allows. Red: a violation, with its statement count (static, plus lazy ones inside functions). The 50 class imports between components and the 24 importlib calls among them are summarised in the red note instead of drawn. The drawings are roadmap/hisim_seams/*.excalidraw (editable) and are inlined below as SVG.

3.1 Proposed

The allowed graph (v5, 2026-11-10). The pipeline is the spine: YAML → energy_system builds the system → the simulator runs it → two frozen records → postprocessing and economics write the result directory. The Python mode builds the system through the simulator's API. RenoVisor wraps the pipeline.

3.3 Where the merged yaml and the drawing differ

Three differences, none silently resolved; Q1 asks the owner to settle them with the graph.

  1. physics_constants is a leaf in the drawing (listed inside the leaves box) and a group of its own in the yaml, importable by every other group. Same edges, one more name.
  2. Registries. The drawing names three (the class loader, the rules registry, describe <class>); the yaml names eight. The five more are hisim.config.base (loads a component class by its MAIN_CLASS path: a config → components load the drawing does not show), hisim.hisim_main (imports the setup file given on the command line), hisim.energy_system.schema_classes and hisim.energy_system.recording.probes (both load components by path) and hisim.components.weather (its lazy facade imports its own submodules).
  3. The faces of config. The drawing draws the declaration API and the construction API as two edges; the yaml has one group config and one edge. The ratchet cannot tell a component that imports ConfigBuilder from one that imports ConfigBase.

5. The seams as records

Five records cross the pipeline's seams. Four are DTOs in the contracts group; the first, BuiltSystem, carries the configured components and so lives with the simulator. 6. Enforcement: the ratchet as merged

Merged in #1262. tests/test_module_graph.py (marker base) parses every import under hisim/ (hisim/inputs excluded) with ast, relative imports resolved, function-local imports included, and checks each against system_docs/module_graph.yaml. TYPE_CHECKING imports count too (they tie the importer to the other group's types and the fix is the same) and are listed in a section of their own because they cause no import cycle. python scripts/module_graph.py check is the same check, readable; report prints the tables below; prune deletes or lowers stale entries.

6.1 The three rules

  1. Edges. A module may import its own group and the groups its group's may_import lists. The yaml refuses a graph with a cycle, and a module that matches no prefix fails with the remedy in the message.
  2. Private names. A name with a leading underscore (not a dunder) is never imported from another group; the group that needs it gets a public spelling.
  3. Imports by string. importlib.import_module, __import__ or a dotted module name passed to a call are allowed only in a registry (table below), and there only of the groups it may_load. Anywhere else, also inside one group, such an import is a violation: it hides an import, usually one that dodges a circular import.

6.2 How a new violation fails, and how the baseline only shrinks

  • Every violation is keyed as (importing module, imported module, imported name or *) with a statement count and a bead id; never a line number, so moving code does not touch an entry. The file is sorted, one entry per line, so two branches that each fixed a violation merge trivially.
  • A violation whose key is not in the baseline fails, and so does one with more statements than its entry. The message names the importer, the imported module, the edge (low -> high) and the two remedies: fix the import, or add the printed entry with a bead id, which needs the owner's approval in review.
  • An entry whose violation is gone, or whose count went down, fails as STALE until it is deleted or lowered: a fix cannot leave room for a later regression. prune does exactly that and never adds or raises an entry.
  • Every entry names a bead that exists in .beads/issues.jsonl; an unknown bead id fails. A pull request that fixes a violation deletes its entries in the same PR; the last one closes the bead.
  • scripts/ratchet.py is the generic core (a baseline per key that may only shrink) and knows nothing about imports; the code-size and escape-hatch ratchets (hisim-repo-cleanup-o6a.12, o6a.13) reuse it.

8. Tests in subdirectories

The target tree mirrors the module groups, so that the path of a test says which seam it exercises:

  • tests/<group>/ for a test that exercises one group (tests/energy_system/, tests/postprocessing/ absorbing test_postprocessing/, tests/economics/, tests/rules/, tests/contracts/, tests/simulator/, ...);
  • tests/components/<folder>/ for a test that imports exactly one component (measured 2026-11-09 over 310 files: 50 such tests, 11 of them of the building, 8 of the heat pump, 7 of the water storage, 6 of the weather);
  • tests/systems/ for a test that builds two or more components (about 64: energy balance, DHW chains, hydronic twins, system setups, sweeps, golden history);
  • tests/tooling/ for the lints, the beads scripts, ci_split, the HPC harness (about 36); tests/_support/ for the 17 helper modules, imported absolutely as tests._support...., so that no test module is imported as a helper.

What moves with the tests: the keys of tests/ci_durations.json (test_ci_split.py reports a stale key), the path p3-parity.yml selects, the Path(__file__).resolve().parents[1] sites that reach the repository root (109 on 2026-11-09; one helper tests._support.paths.REPO_ROOT replaces them), an __init__.py per new directory (import mode prepend, as today, so a basename may repeat across directories). Markers, the root conftest.py and the two package conftests stay. 10. Open questions for the owner

Each question gives the context, the options and a recommendation marked as such. Nothing below is decided.

Q1. Is the graph of system_docs/module_graph.yaml the design? The file is merged and enforced but calls itself a draft. Approving it fixes the 18 groups, their edges and the eight registries, including the three differences to the drawing in §3.3: physics_constants as a group of its own, the five extra registries (above all hisim.config.base loading a component class by MAIN_CLASS, an edge from config to the components the drawing does not show), and config as one group rather than two faces. Recommendation: approve the yaml as it is; the registries are measured facts, and a loaded class is not an import the type checker sees. If the faces should be enforced, split hisim/config into two packages later; a group is a prefix, so the yaml then changes by two lines.
Q2. The name of the shared code. The yaml and the drawing say hisim/components/shared/: inside the components package, next to what uses it, but then a reader must know that the longest prefix wins to see it is its own group. The alternative is a top-level hisim/shared/ beside hisim/subcomponents/: visible in the tree, one more top-level package. Recommendation: hisim/components/shared/, as the yaml already names it; the shared code is the components' own vocabulary and nothing above the components may import it.
Q3. Who calls post-processing and economics, and one record or two. As drawn, the simulator freezes the two inputs and calls both engines itself, so the yaml lets the simulator import postprocessing and economics. The alternative: the simulator returns the records and the driver (energy_system, hisim_main) calls the engines; the simulator then needs neither, and a driver can skip one. Independently: two typed records as drawn, or one record with two views (less to freeze, but each engine sees the other's fields). Recommendation: the simulator calls both, as today and as drawn (one place that owns the sequence for both modes); two records, so that each engine's input is exactly what it reads and the ratchet proves it.
Q4. The AFTER_RUN energy balance. The AFTER_RUN rules judge the run's energy balance, which post-processing computes (EnergyBalanceReport); the yaml lets setup_rules import postprocessing for it (orange in the drawing). The alternative: a contracts type the driver computes once and hands to both the rules and the post-processing, so setup_rules imports nothing of postprocessing. Recommendation: keep the edge; the balance is post-processing's result, and moving its computation into contracts would put behaviour there.
Q5. How RenoVisor reads the run's KPIs and balance. It needs more than the lifecycle costs (owner). As drawn, through post-processing's readers over the result directory (KpiFinder, the balance report): one reader shared with the Sankey CLI, and RenoVisor keeps an import of postprocessing. The alternative: the raw files (all_kpis.json, balance_report.json) with RenoVisor's own reader, so RenoVisor depends only on file formats. Recommendation: the readers, as drawn; a second parser of the same files is a second place that breaks when a KPI name changes.
Q6. The default connections. 50 class imports and 24 importlib calls exist between components so that A can name B's class and outputs in get_default_connections_from_B, both ways round; the ratchet cannot see the 50 (§6.4). Options: (a) allow a component to import another's public API for its default connections, acyclically: impossible while both sides declare the connection, so the importlib dodges stay; (b) tolerate them permanently on the baseline: the lint then says nothing about the components; (c) the connections name their partner by string (class name, output name) and one generic test checks that every named class and output exists, later matched by role (load type, unit, tag, as hisim.config.channels already does), so that no component imports another. Recommendation: (c), as its own bead under the epic; interim (b) under hisim-repo-cleanup-o6a.15 for the 24 calls so that the folder PRs need not wait. No bead is filed for (c) yet.
Q7. The recorded class path of a packaged component. Today both spellings exist: hisim.components.weather.Weather (the package; 41 YAMLs) and hisim.components.building.building.Building (the defining module; 39 YAMLs, and #1241's heat-pump paths). The package path lets a folder be reorganised without touching a twin, and the public API and the recorded name coincide; the module path names the file to open but changes on every reshuffle inside the folder, which is the churn this epic exists to remove. Recommendation: the package path, with the recorder deriving it from the nearest package whose __init__ exports the class, and a one-time rewrite of the building and heat-pump paths.
Q8. The tariff provider's split. hisim.components.tariff_provider imports the engine's tariff contract, the spot-series loader and the marginal-price function (10 entries). Options: (a) the tariff types move to contracts and the reader is handed in through the configuration; (b) the component gets its prices as an input from a data source that reads the contract, so the component holds no tariff code; (c) the tariff module becomes a leaf the engine and the component both import. Recommendation: (a); it keeps one tariff contract, read in one place, and the component's configuration stays plain. The bead names this as the owner's decision.
