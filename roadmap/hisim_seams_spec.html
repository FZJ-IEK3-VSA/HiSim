Spec: the HiSim repository gets a layer map enforced by one test, every multi-module component in a folder of its own, and a tests tree that mirrors the packages

Status: draft, nothing decided, nothing merged. Owner: Noah Pflugradt. Epic: hisim-ylxf (P1). Builds on: the four import lints (tests/test_renovisor_import_lint.py, tests/test_economics_import_lint.py, tests/test_energy_system_layering.py, tests/test_subcomponent_import_lint.py), the config layer rule (hisim/config/__init__.py), the heat-pump package #1241, and beads hisim-repo-cleanup-o6a.15, o6a.4, o6a.29, o6a.31 and hisim-rust-ideas-9ks.2. All numbers were measured on origin/main at 911498220 (2026-11-09) by the scripts in agent-tmp/seams/ (not in the repository; the tables they wrote are listed in the appendix). The owner's goal, in his words: "start working on the seams for hisim to limit the blast radius of changes as much as possible."

1. Problem

HiSim has 356 Python modules under hisim/ (the inputs data tree excluded): 33 modules directly at the top level and 10 code packages. Four import rules are enforced today, each by its own test; everything else may import anything. Measured on main:

  • The eight code packages form one strongly connected component. Counting a package's static imports only, config, the top-level modules, caching, components, postprocessing, setup_rules, energy_system and economics all reach each other. There is no layer below which a change is safe.
  • The root is the component base class. hisim/component.py imports hisim.economics.facts (for CostRelevance) and hisim.postprocessing.kpi_computation.kpi_structure (for KpiEntry). Through it, every component depends on the cost engine and the post-processing: 49 component modules import economics.facts, 31 import kpi_structure, 21 import capex_computation. 105 of the 156 violating import statements of §4.1 come from these three modules sitting above the components.
  • Cycles are hidden, not absent. No module-level cycle exists among top-of-file imports, because the cycles were broken by hand: 86 function-local imports of HiSim modules and 36 importlib.import_module calls, 24 of them in components with the comment "use importlib for importing the other component in order to avoid circular-import errors". With those imports counted, three module cycles reappear (8, 6 and 5 modules, §4.2).
  • Components import each other. 76 static and 14 lazy imports run between modules of hisim/components, against the black-box principle of system_docs/component_design_principles.md B.1. Most name another component's class for a default connection or reach a shared helper that is filed under components (configuration.py, dual_circuit_system.py, heating_curve.py).
  • A change to one component touches the whole repository. #1247 (PV publishes its DC power) changed 3 component modules and 86 other files: 37 energy-system YAMLs, 16 system setups, 27 tests. #1241 (heat pump into a package) moved 5 modules and changed 62 other files. The twins, the goldens and the tests cannot say which of them a change affects, so every change re-runs everything.
  • The tests tree does not mirror the packages. 310 test files sit flat in tests/ beside 16 helper modules; 9 subdirectories hold 78 more. "Which tests does this change affect" cannot be read off a path.

2. Decisions

None taken. Every choice is an open question in §11 with a recommendation; the owner decides. Only the bead text of hisim-ylxf is the owner's: every multi-module component in a folder of its own, a written layer map enforced by one import-lint test, explicit public APIs between packages, recorded paths migrated with a mapping that fails loudly on an old path except where written down, child beads per step before the work starts.

3. Terms

  • Layer: a named set of packages and modules. A module may import a layer below its own; never its own layer's siblings (except where the map lists it) and never a layer above.
  • Package: a directory under hisim/ with an __init__.py, for example hisim.energy_system. A component folder is a package under hisim/components/.
  • Public API of a package: the names its __init__.py exports (__all__). Everything else in it is internal. Another package imports only the public API; a module inside the package imports its siblings freely.
  • Seam: the boundary between two packages, crossed only through the public API in the direction the layer map allows.
  • Static import: an import statement at module level. Lazy import: one inside a function or method (resolved when the function runs). Hidden import: a module loaded by importlib.import_module or __import__ with a string.
  • Class path: the dotted module path plus class name an energy-system file writes under class:, for example hisim.components.weather.Weather. The recorder derives it from the class's __module__.
  • Allow-list: the committed list of today's violations the lint tolerates, each with the bead that removes it. A ratchet is an allow-list that may only shrink: an entry no longer needed fails the test until it is deleted.
  • Blast radius of a change: the set of tests, goldens and recorded files that can be affected by it.

5.1 How "affected tests and goldens" becomes computable

Once the map and the folders exist, a script (scripts/affected_tests.py, a child bead) derives the set from a diff:

  1. Changed units. Map every changed file to its package or component folder through the layer map; a changed file under tests/ maps to itself; a changed energy_systems/*.yaml maps to that twin.
  2. Dependents. Close the set upward over the measured import graph at package granularity (the lint already computes it): a change in hisim.components.generic_pv_system affects the packages that import it (the layers above), and nothing beside or below it. A change in L0 or L1 affects everything; that is the honest answer for the component model.
  3. Tests. The tests of every affected package are the directory that mirrors it (§9) plus the system tests whose twins contain an affected component (step 4). A test outside those directories is unaffected unless it imports an affected module, which the same import scan tells.
  4. Twins and goldens. A twin is affected when an entry's class: lies in an affected package. The golden pairs are golden_references/<setup>__<params>.json of those twins. For #1247 that is 29 twins; for a change inside the district-heating component it would be the 4 twins that contain one, for the car the 2.
  5. Output. The pytest paths, the golden pairs and the twins to re-record, as the input of golden-check.yml's --pairs and of a path-selected pytest run. Marker-only selection stays for the full runs on main; selective runs are for pull requests.

Owner memory defers Pants, doc-only skips and affected goldens until this epic lands; steps 1–4 are what those need, and the import scan of the lint is the one place that computes the graph.

7.2 The allow-list policy

Options for the 156 statements that violate the map on day one:

  • Fix first: no lint until every violation is gone. Rejected: 156 statements across 90 modules is weeks of PRs, and the seams keep getting worse meanwhile.
  • Package-level allow-list ("components may import economics until bead X"): coarse, lets new violations in under an existing entry. Rejected.
  • Module-level ratchet: one entry per (importing module, imported module), each with the bead that removes it. A new violation fails; an entry whose import is gone fails until deleted. Recommended. The first PR commits today's list (about 90 entries after the contracts move is written as one bead, since the lint can list the 105 statements under three entries keyed by the imported module).

8.2 How recorded paths migrate

  1. The class-path convention is settled first (Q3). If the package path wins, every packaged class pins __module__ to its package as the weather does, the recorder writes the package path, and a one-time rewrite brings the 40 building.building.Building files and the three heat-pump paths to it. If the defining module wins, the weather and PV spellings are rewritten the other way and the weather facade's __module__ pin goes.
  2. Every move PR rewrites the recorded files in the same PR: energy-system YAMLs (scripts/record_all_setups.py --check proves the twins byte-equal afterwards), the schema (hisim energy-system schema), MAIN_CLASS, the translation map (python -m hisim.renovisor map), tests and docs. #1241 did exactly this for 10 YAMLs.
  3. A moved path is written down in hisim/energy_system/moved_class_paths.yaml: old path, new path, PR, date. The loader's refusal EF-10 CLASS_NOT_IMPORTABLE looks the old path up and says the new one ("'hisim.components.generic_car.Car' moved to 'hisim.components.car.Car' in #N"). It still refuses: that is the "fail loudly" of the bead. Whether an entry may also alias is Q4.
  4. Goldens stay valid without change (§4.7: no class path in a golden). A move PR is a refactoring commit free of result changes; the golden check runs on it and must pass bit-identically, as it did for #1241.
  5. RenoVisor bindings stay valid as long as the grouped twins it edits are re-recorded in the same PR; the translator never writes a class path. The capability document and tests/renovisor/test_map.py catch a stale translation_map.html.

8.3 The default connections

24 importlib calls and about 30 of the 76 static component-to-component imports exist so that component A can name component B's class and outputs in get_default_connections_from_B, while B names A in its own. These are the cycles of §4.2. A folder structure does not remove them; they go only if the connection tables leave the components (Q2): the declarative wiring of hisim.energy_system and its assemblies already holds the same knowledge as data, and hisim.config.channels already matches ports by load type, unit and tag. Until that is decided, the default connections are allow-list entries of one bead.

Q10 decides; the absolute spelling is recommended.
  • Markers. Unchanged: a test keeps its job marker and job_markers.py keeps checking it. A directory conftest may add a marker as assemblies/ does, but no new one is proposed.

  • Sibling files. tests/goldens/, tests/energy_systems/ and tests/worked_examples/ are data read by tests that move; they stay where they are and are reached through the same helper.
  • __init__.py and duplicate basenames. Every new directory gets an __init__.py (rootdir mode prepend, as today), so a basename may repeat across directories as the five existing duplicates already do. Within one directory the names are unique by construction.

9.3 Place in the PR plan

Two orders are possible. One mechanical move first (one PR, 310 renames plus import fixes) conflicts with every open PR that adds or edits a test: #1247 (27 tests), #1252–#1254 (18 tests) and #954 would each need a rebase that git resolves badly for a renamed file. One move PR per target directory after the layer map lands conflicts only with PRs touching those tests, and each PR is reviewable. Recommended: per directory, after the lint PR, starting with the directories no open PR touches (economics, postprocessing, rules, tooling), the component folders as each folder PR lands, systems last.

11. Open questions for the owner

Each question gives the context, the options with their consequences, and a recommendation marked as such. Nothing here is decided.

Q1. The layer order. §6 proposes eight layers with the simulator above the post-processing (the run calls it) and the concrete setup rules above the energy-system format (they read its model). Alternatives: (a) post-processing above the simulator, with the simulator handing it a result object: cleaner in theory, but simulator.py calls PostProcessor today and the result object does not exist yet, so it costs a refactor before any lint can pass; (b) keep setup_rules as one package and place it above energy_system: then the 30 imports of the engine from energy_system and the simulator stay violations forever. Recommendation: the order of §6, with the setup-rules split.
Q2. May components import each other at all? The black-box principle says a component sees another only through its ports. Today 76 static, 14 lazy and 24 hidden imports exist, in three groups: (i) shared helpers misfiled under components (configuration, dual_circuit_system, heating_curve's EmitterDesign): go to the foundation or subcomponents regardless; (ii) the modules of one component spread over several files (car, LPG, electrolyzer, fuel cell): become one folder, where importing a sibling is internal; (iii) default connections naming another class and its outputs, in both directions (building ↔ heat distribution, storage ↔ heat pump, EMS → nine components). Options for (iii): (a) allow a component package to import another's public API for its default connections only, acyclically: impossible as long as both sides declare the connection, so the importlib dodges stay; (b) allow it cyclically through lazy imports in get_default_connections_* methods, listed in the allow-list without an end date: makes the lint lie about the components; (c) forbid every import between component folders and move the default connections out of the components into data that the wiring layer reads (the assemblies already express the same connections declaratively; config.channels already matches ports by tag): the imperative setups then get their defaults from the same table through the simulator's connect_automatically. Recommendation: (c) as the rule, with (b) as the interim allow-list under one bead, so the lint shows the debt and the folder PRs do not wait for it. Where the class name is needed as a string only (get_classname()), the port vocabulary belongs in the folder's public API, not the class.
Q3. The class-path convention. A packaged component is spelled three ways today (§4.7). Options: (a) the defining module (…more_advanced_heat_pump.heat_pump.MoreAdvancedHeatPumpHPLib, as #1241 chose): the path tells a reader which file to open, but every later reshuffle inside the folder changes recorded files, which is the churn this epic exists to remove; (b) the package (…weather.Weather): a folder can be reorganised without touching a twin, the public API and the recorded name coincide, but the recorder needs the __module__ pin or a lookup of the class in its package's __all__, and #1241's three paths plus 40 building files are rewritten once. Recommendation: (b), with the recorder deriving the path from the nearest package whose __all__ exports the class, so no __module__ pin is needed.
Q4. Alias period or clean break for moved paths. #1241 broke cleanly: an old path is refused with EF-10 and no "did you mean". Options: (a) clean break plus the recorded mapping, so the refusal names the new path and the PR number (the bead's "fail loudly, except where written down" read as: the written-down entries make the message, not an alias); (b) an alias period in which moved_class_paths.yaml entries younger than N releases resolve with a warning: convenient for external users with old energy-system files, but HiSim has no external declarative users today and an alias delays the rewrite of every twin. Recommendation: (a). The mapping file exists either way, so (b) can be switched on later if an external user appears.
Q5. import-linter or HiSim's own test. §7.1. Recommendation: the own test, because it sees the hidden imports, keeps the map and the allow-list in one document, folds the four lints into one, runs in pytest -m base and adds no dependency. import-linter stays the fallback.
Q6. The allow-list policy. §7.2. Options: fix first; package-level entries; module-level ratchet with bead ids and stale-entry failure. Recommendation: the module-level ratchet. A second choice inside it: may a PR add an entry? Proposed: only with a bead id, and only in a PR that the owner approves for it; the test says so in its failure message.
Q7. May post-processing import components? Today 9 imports, all to read a meter's or generator's results by its class. Options: (a) allow downward imports of component public APIs from post-processing: legal under a pure layer rule, but a new component then needs a post-processing edit (shotgun surgery, coding_style.md §3) and the post-processing cannot be tested without components; (b) forbid it: post-processing reads by KPI tag, port role (energy_port) and component kind, which the results already carry. Recommendation: (b); the 9 imports are one bead (step 5).
Q8. Where the CLI lives. Eight entry-point modules sit at the top level (cli.py, four cli_*, hisim_main.py, hisim_with_profiler.py, project_code_overview_generator.py). Options: (a) a package hisim/cli/ with hisim_main.py kept at the top as the documented script path (python hisim/hisim_main.py appears in README, CLAUDE.md, AGENTS.md and the quality workflow); (b) everything into hisim/cli/ and a two-line hisim/hisim_main.py that calls it; (c) leave them flat and list them as layer L6 in the map. Recommendation: (b); the console script hisim=hisim.cli:main becomes hisim.cli.main:main.
Q9. Folder policy. The bead says "every component that spans more than one module". Options: (a) only those (seven folders, §8.1), the single-module components stay flat: least churn, but two shapes coexist and a test directory per component mirrors only the folders; (b) every component in a folder, also the single-module ones (about 40 more folders, each one module and an __init__): one shape, one test directory per component, at the cost of 40 trivial moves and recorded-path rewrites (none if Q3 picks the package path and the folder is named after the module). Recommendation: (a) now, (b) folder by folder when a component is next touched, never as one sweep.
Q10. The tests layout. Options: (a) mirror the package tree strictly (tests/components/car/, tests/energy_system/, …) with a systems/ directory for tests that build several components and a tooling/ directory for tests of scripts and CI: the path says what a test exercises, which §5.1 needs; (b) group by topic (hydronics, DHW, electricity, costs): reads well for people, but a topic spans packages and the path says nothing a tool can use. Inside (a), two sub-questions: where do the energy-balance and golden tests go (proposed: systems/, since they build whole systems; their twins decide their blast radius, not their directory), and how helpers are imported (proposed: absolute tests._support.…, which keeps working from any cwd and any directory depth). Recommendation: (a) with systems/, tooling/ and _support/.
Q11. Move the component-model modules into hisim/core/? The lint needs no move: the map lists the modules. A package makes the layer visible in the tree and lets tests/core/ mirror something, at the price of rewriting 106 import sites of hisim.component, 71 of simulationparameters and 117 of loadtypes if the leaves move too, in every open PR's path. Recommendation: not now; list the modules in the map, decide again when the stack of open PRs is short.
Q12. The name and home of the declaration types. KpiEntry, CostRelevance and the capex proration must sit below the component base class. Options: (a) a new package hisim/contracts/ (three modules): names the idea, one place; (b) inside hisim/config/: already the bottom layer, but config is about configuring, not about what a component publishes; (c) three top-level leaf modules (hisim/kpi_structure.py, …): no new package, but the top level grows again. Recommendation: (a).

12. Beads

Epic hisim-ylxf. The child beads are the rows of §10; they are created with br on the branch of the first PR, each with kind chore (a move or a lint) or task (the contracts leaf, the affected-tests script), area components, ci or postprocessing as the change lands, priority P2 for steps 1–7 and P3 for the rest, and owner-decision on the twelve questions above until they are answered. Beads folded in: hisim-repo-cleanup-o6a.15 (steps 1, 2, 4, 6, 16), o6a.4 (step 6), o6a.29 and o6a.31 (steps 12 and 15); hisim-rust-ideas-9ks.2 (one adapter per physics library) is referenced, not folded: an adapter module is internal to its component folder under this map, and the folder PRs leave room for it.
