# `roadmap/renovisor/` — what to read, and in which order

Design record of the RenoVisor translation layer (`hisim/renovisor/`). The code is documented in
`hisim/renovisor/how_to_use.md` and in the package's own docstrings; what lives here is the
reasoning: what was decided, against which sources, and what was tried and dropped.

## Current

Read these to understand the layer as it stands.

1. `challenges.md` — the decision register, and the only binding document in this directory.
   Read **§13** first (the decisions of 2026-09-19 that settled the shape the code has), then
   **§12** and **§9** for the questions those decisions answer.
2. `review_translator_spec_v2_2026-09-19.md` — the review of the frontend side's translator
   specification v2, which §13 adopted; it says what was accepted, what was corrected and why.
3. `implementation/step8_reconciliation.md` — the implementation specification the current code
   was written from, module by module. Its **§13 addendum** records what the first generated
   capability document changed.
4. `implementation/step9_cleanup.md` — the specification of the cleanup this directory and the
   test layout went through.
5. `translation_map.html` — the whole translation as one page: every request field, every
   measure, every result field, with what happens to it. Generated by
   `python -m hisim.renovisor map`; open it from the file system.
6. The vendored contract under `hisim/renovisor/contract/` — the frontend side's own
   `calculation-request.schema.json`, `measures.yaml`, `materials.yaml` and the worked mockup,
   each pinned to the revision it was copied from in `PINNED.yaml`. These are the authority on
   what a request may say; nothing here overrides them.

## History

Kept for the reasoning, in the order they were written. None of them is current, and where they
disagree with `challenges.md` §13, §13 wins.

1. `requirements.md` (2026-08-27) — the first statement of what a RenoVisor calculation library
   has to do, with the R/A/Q ids the later documents reuse.
2. `requirements.discussion.md` — the alternatives considered and rejected while `requirements.md`
   was written; explicitly not binding.
3. `field_inventory.md` — the counted field-by-field survey of the v0.3 contract against HiSim,
   which is where the gap list came from.
4. `measures_v2_requirements.md` (2026-09-13) — what the measure catalogue v2 demanded of HiSim,
   measure by measure.
5. `implementation/step3_pure_layers.md` … `step7_contract_pr.md` — the specifications of the
   first implementation, whose module layout (`catalogue`, `options`, `registry`, `effects`,
   `inventory`, `application`, `base_files`) step 8 replaced.
6. `contract_rewrite_proposal.md` — the proposal to rewrite the contract's `openapi.yaml` from
   the simulation's side, superseded when the frontend side's own specification was adopted.

Two artefacts were deleted in step 9 and live in git history only: `contract_rewrite.diff` (the
diff of the superseded contract branch) and `mockups/` (`heat_pump_household.energy_system.yaml`
and `measures.schema.yaml`, the August design the catalogue superseded; the decisions their
footers carried are recorded in `challenges.md`). The history documents above still name them.
