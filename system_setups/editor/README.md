# HiSim Scenario Editor

A browser-based visual editor for `*.scenario.json` files. Components appear as cards in a node-graph canvas; ports are connected by bezier curves. Built with Vite + React + TypeScript + React Flow + Tailwind CSS + Zustand.

---

## What the editor is for

A HiSim scenario is a list of components plus a list of connections between their ports. Written by hand that is a few hundred lines of JSON in which the wiring — the part that actually defines the energy system — is the hardest thing to see. The editor exists to make that wiring visible and directly manipulable. Four uses:

| Use | What you do |
|---|---|
| **View** | Open an existing `*.scenario.json` and read the system as a graph: which component feeds which, and with what quantity. |
| **Modify** | Change a config value, rewire a connection, add or remove a component — then write the file back out. |
| **Create** | Build a scenario from scratch by dragging components from the palette and connecting their ports. |
| **Debug** | Find what is wrong with a scenario before running it: unconnected mandatory inputs, duplicate component names, unit mismatches across an edge, connections pointing at ports that no longer exist. |

It is an editor for the **scenario** file only. Simulation parameters (time range, resolution, post-processing options) live in a separate `*.simulation.json` and are not edited here. The editor also does not run simulations — you save the JSON and hand it to `hisim_main.py`.

Everything the editor knows about components comes from `component_db.json`, which is generated by introspecting the actual Python classes (see below). So the palette, the ports, the config fields, and the defaults are always whatever the current source says they are — there is no hand-maintained model of HiSim inside the editor.

## One-time setup

From the repo root, activate your Python environment and install the HiSim package if you haven't:
```bash
pip install -e .
```

Then install the editor's JavaScript dependencies:
```powershell
cd system_setups/editor
npm install
```

## Generating the component database

The editor reads two static JSON files that describe all HiSim components and their ports. Re-generate them whenever you add or modify components:

```bash
# from the repo root, with hisimvenv active
python tools/generate_component_db.py
```

Output files (committed to the repo so the editor works without running the script):
- `system_setups/editor/public/data/component_db.json` — one entry per discovered component (82 at the last regeneration) with inputs, outputs, config fields, and default connections
- `system_setups/editor/public/data/enum_db.json` — all LoadTypes, Units, ComponentType, etc. enums
- `system_setups/editor/public/data/catalog_db.json` — dropdown data (weather datasets, PV modules and inverters, heat pump models)
- `system_setups/editor/public/data/usage_db.json` — how often each component appears in the shipped `system_setups/*.scenario.json`, alongside which others, and which dynamic output channels they declare; drives *Suggest components* and the dynamic-port offers

The script exits non-zero if any component fails introspection; failures are listed in `component_db.json` under `"failures"`.

```powershell
cd system_setups/editor
npm run build       # output goes to system_setups/editor/dist/
npm run preview     # serve the built output locally for a final check
```

`npm run preview` opens at `http://localhost:4173` — Vite's preview default, a different port from the dev server's 5173, so both can run side by side. Unlike `npm run dev` it serves the built `dist/` output with no hot-reload, so re-run `npm run build` after every change you want to see.

## Using the editor

### The screen

```
┌──────────┬──────────────────────────────────────────────┬────────────┐
│          │  Toolbar   New · Open · Save · Undo/Redo ·   │            │
│ Palette  │            Validate · Suggest components ·   │ Inspector  │
│          │            Auto-connect · Auto-layout ·      │            │
│          │            Auto-edges                        │            │
│          ├──────────────────────────────────────────────┤ scenario   │
│ search + │                                              │ metadata,  │
│ compo-   │  Canvas — component cards + connections      │ or config  │
│ nents by │                                              │ of the     │
│ category ├──────────────────────────────────────────────┤ selected   │
│          │  Status bar — validation results             │ node       │
└──────────┴──────────────────────────────────────────────┴────────────┘
```

The Inspector shows **scenario metadata** (name, description) when nothing is selected, and the **config of the selected component** when a card is clicked. Click empty canvas to deselect and get the metadata back.

### Creating a scenario from scratch

1. **`New`** — clears the canvas and resets the scenario name.
2. **Set the scenario name and description** in the Inspector (nothing selected). The name becomes the downloaded filename, so `Basic Household` → `basic_household.scenario.json`.
3. **Drag components** from the palette onto the canvas. The search box filters by display name and category; the `dyn` badge marks a `DynamicComponent` (variable number of ports, resolved at runtime).
4. **Configure each component**: click its card, then fill in the Inspector. Fields marked `*` are required. The **Instance name** is what connections refer to in the JSON — it must be unique, and it stays in sync with the config's `name` field.
5. **Wire the ports**: drag from an output handle (right edge of a card) to an input handle (left edge). A drop is refused if the units don't match — a `W` output cannot be dropped on a `°C` input. HiSim passes the raw number straight down the channel and never checks it, so nothing would catch such a wire at runtime; the editor blocks it here instead. Unitless ports (`-`, i.e. `Units.ANY`) accept anything.
6. **`Auto-connect all`** wires up everything the components declare as default connections, wherever exactly one matching source sits on the canvas. These edges are drawn **dashed**. Ports it could not resolve (no candidate, or several) are flagged `⚠` on the card and listed in the Inspector — wire those by hand. To do just one component, right-click its card → **Auto-connect this**.
7. **`Suggest components`** — when you are not sure what the system still needs, this works it out from what is already on the canvas. See [below](#suggest-components).
8. **`Auto-layout`** arranges the cards left-to-right along the data flow. Purely cosmetic; positions are saved with the file.
9. **`Validate`** — results land in the status bar; click it to expand the list.
10. **`Save JSON`** downloads `<scenario_name>.scenario.json` to your browser's download folder. Move it into `system_setups/`.
11. **Run it** (from `system_setups/`, with `hisimvenv` active):
    ```bash
    python ../hisim/hisim_main.py my_scenario.scenario.json 2021_minutely_plots.simulation.json
    ```

### Opening and modifying an existing scenario

1. **`Open JSON`** → pick any `*.scenario.json` (e.g. from `system_setups/`).
2. The graph is rebuilt: cards, explicit connections, and — for components with `connect_automatically: true` — their default connections as dashed edges. Card positions come from `_editor_positions` if the file was written by the editor before, otherwise from auto-layout.
3. Anything the importer had to drop (a component missing from the registry, a connection naming an unknown port) is reported in the status bar, and validation runs immediately.
4. Edit as above, then **`Save JSON`**. The download **replaces nothing** — it lands in your download folder and you copy it over the original yourself, so the source file is never overwritten behind your back.

### Debugging a scenario

**`Validate`** classifies findings by severity, all shown in the status bar:

| | Meaning | Examples |
|---|---|---|
| ✗ **error** | The scenario will not run correctly | mandatory input not connected · duplicate component name · edge attached to a port that does not exist |
| ⚠ **warning** | Probably wrong, will run anyway | unit mismatch across an edge (a `W` output feeding a `°C` input) · required config field left empty |
| ℹ **info** | Noise-level, usually fine | optional input not connected · load-type mismatch across an edge (a labelling inconsistency HiSim ignores — the shipped setups are full of them) |

Infos are collapsible so the two severities that matter stay readable.

Some checks run **continuously**, without pressing `Validate`: a card with an unconnected mandatory input or a duplicated name gets a red ring, the offending port turns red, and a duplicate name shows a `dup` badge.

A validation result is a **snapshot**, so the status bar says when it stopped being one: edit anything after validating and it shows `⧗ validation out of date — validate`; put components on the canvas without ever validating and it shows `⧗ not validated`. Click that to re-run. **`Save JSON`** refuses to write silently in either state — see [Saving without a valid check](#saving-without-a-valid-check).

### Suggest components

Building a scenario from scratch means knowing which components a working system needs — the part that is hardest to get from the component list alone. **`Suggest components`** (toolbar, and in the status bar whenever there are open errors or warnings) works it out from the canvas and proposes additions you can accept with one click. Each proposal is added with its default config and immediately auto-connected, to it and to anything else that was waiting for it.

It answers in three sections:

| Section | Where it comes from | Reliability |
|---|---|---|
| **Would fill an unconnected input** | Every input port with nothing feeding it. If the component declares a `default_connections` entry for that port, the source class and output port are read straight off it; otherwise a registry component with a unit-compatible, similarly named output is offered as a guess (marked *(guess)*). `✗` = mandatory (a validation error), `ℹ` = optional. | High. Deleting a component from a shipped scenario and asking what is missing brings it back ranked first 91% of the time, and in the top three 98% — whenever the deletion left a mandatory input open. |
| **Already on the canvas — not wired up** | Same analysis, but the source component is already there and only the connection is missing. One click per wire; `Auto-connect all` does the declared ones in bulk. | High — same evidence. |
| **Commonly used together** | Counted across the shipped `system_setups/*.scenario.json`: *"N of the M scenarios with a Weather also have an ElectricityMeter"*. On an empty canvas this becomes *Common starting points*. | Statistical, not structural. This is the only thing that can see a component nothing **declares** a need for — delete a battery, or a PV system that feeds a meter through a dynamic port, and no port is left unconnected. Port analysis recovers 12% of those; co-occurrence names them first 67% of the time. |

Nothing here is authoritative about *your* system: the first two sections say what the components themselves declare, the third says what other scenarios happen to contain. Added components arrive with default configuration — open the Inspector and check it.

### Saving without a valid check

`Save JSON` asks before writing whenever the validation result does not describe the scenario you are about to export:

- **never validated** — nothing has been checked at all;
- **out of date** — the scenario changed after the last validation, so the status bar describes an earlier version of it;
- **validated, with findings** — errors or warnings are still open.

The first two offer **Validate first**, which re-runs the checks and then exports straight away if they come back clean. Every case also offers **Export anyway** — the editor blocks nothing, it only refuses to let a stale check pass for a real one.

### Dynamic components

Five components (`ElectricityMeter`, `GasMeter`, `FuelMeter`, `HeatingMeter`, and the EMS
`L2GenericEnergyManagementSystem`) declare no fixed input ports. They grow **one input per
component they measure or control**, so what you see on the card depends on the rest of the
canvas. They carry a `dyn` badge in the palette, and their ports are shown in *italics*.

Such a port comes into existence in one of three ways, and the editor shows all three:

| Route | When HiSim creates it | In the editor |
|---|---|---|
| **Declared default** | At start-up, for any dynamic component with **`Connect automatically`** on: `prepare_calculation` walks every component in the setup and adds an input for each one whose class the target declares in `dynamic_default_connections`. | Appears by itself as soon as both components are on the canvas, connected with a dashed edge and marked `auto` in the Inspector. **Not** written to the file — HiSim recreates it, and writing it too would create the port twice. |
| **Declared by the scenario** | At build time, from the `inputs[]` array, whatever the toggle says. | Switch `Connect automatically` **off** and the Inspector offers the same ports under *Dynamic ports* with an `Add` button. These are written to the file. This is the form the shipped scenarios use. |
| **Written by hand** | Never automatically — only where a Python setup calls `add_component_output`. | Output channels such as the EMS's `LoadingPowerInputForBattery_` are offered in the Inspector whenever the component they drive (a `Battery`) is on the canvas, taken from what the shipped scenarios declare. One click adds the port *and* the connection. |

So `Connect automatically` on a dynamic component is not cosmetic: **on** means "the simulator
works out my inputs", **off** means "the file states them". Both run; the shipped scenarios
mostly use the second, and the Python system setups mostly use the first.

One trap the editor now catches: `Connect automatically` on a component that declares **no**
default connections at all — a `Weather`, an occupancy profile, a `Battery` — makes HiSim raise
`KeyError` at start-up, before the first time step. New components are created with the toggle
in the right position, and `Validate` reports any that are wrong.

### Reading the canvas

- **Port and edge colour** = load type (electricity, heat, water, …), so a mis-wire is usually visible before it is validated.
- **Solid edge** = an explicit connection stored in the file. **Dashed edge** = an auto-connection derived from the component's declared defaults. Toggle dashed edges off with **`Auto-edges ●/○`** in the toolbar to see only what the file itself specifies.
- **Italic port labels** = dynamic ports declared by the scenario rather than by the component class.
- `*` after a port name = mandatory input. `⚠` = auto-connect found no unique source for it.
- Click a card **header** to expand it and show the first config values inline.
- Hover any port label for its full name, load type, and unit.

### What `Save JSON` writes

The exported file contains `name`, `description`, `multiple_buildings`, `components` (class name, configuration, dynamic ports, `connect_automatically`), and `connections`. Two things are deliberate:

- **`_editor_positions`** — canvas coordinates keyed by component name. HiSim ignores this field; it exists so reopening the file restores your layout.
- Auto-connected edges are **omitted** from `connections` when their target has `connect_automatically: true`, because HiSim recreates them at runtime. Turning that toggle off for a component (Inspector → *Connect automatically*) makes its connections explicit in the file instead.

### Keyboard

| Key | Action |
|---|---|
| `Delete` / `Backspace` | delete the selected node(s) or edge(s) |
| `Ctrl+Z` | undo |
| `Ctrl+Y` / `Ctrl+Shift+Z` | redo |
| right-click a card | context menu (auto-connect, delete) |

Undo/redo covers node and edge changes (add, delete, move, connect, auto-connect, auto-layout); it does **not** cover config edits in the Inspector, where the browser's own text undo applies.
